## Prioritized issues / release blockers

### P0 — Must be addressed before any public production release

**P0-01 Android update identity and reliable signing are NOT established (VERIFIED SOURCE).** `android/app/build.gradle` still has `versionCode 38`, `versionName '0.9.21-game-feel'` in a v0.9.25 preview. CI output is a debug-signed test APK with potentially different debug keys; bundle is unsigned. The reusable `publish-preview-apk.yml` enforces a tag/versionName match, so a future v0.9.25 preview tag would fail its guard without versioning work. Require monotonic versionCode, accurate versionName, controlled signing key/backup custody, debug-to-prod migration policy, safe app-data update test, and a real install/update/uninstall matrix. [Signing #20](https://github.com/PlayerEden/Ricochet-Rumble/issues/20), [release #30](https://github.com/PlayerEden/Ricochet-Rumble/issues/30).

**P0-02 No approved integrated production baseline (VERIFIED SOURCE).** The mainline game code is still v0.9.21. Draft PRs [#24](https://github.com/PlayerEden/Ricochet-Rumble/pull/24), [#31](https://github.com/PlayerEden/Ricochet-Rumble/pull/31), [#32](https://github.com/PlayerEden/Ricochet-Rumble/pull/32), [#34](https://github.com/PlayerEden/Ricochet-Rumble/pull/34), [#35](https://github.com/PlayerEden/Ricochet-Rumble/pull/35), [#39](https://github.com/PlayerEden/Ricochet-Rumble/pull/39) are a *stacked prototype history*, with audit #40 extending it further. They must not be clicked Merge one after another. Retain stable main/tag and immutable v0.9.25 known-good, reconcile ancestor commits and owner phone acceptance, make one conscious integration candidate, rerun full QA, then merge only after acceptance. No unapproved merge conducted here.

**P0-03 Actual scored modes are NOT yet playable (VERIFIED SOURCE).** The score kernel is an ESM file without browser/Android import. A real scored round requires authoritative incident IDs from actual pilot deaths, unlimited respawn loops/clock, tie results and new HUD/After Action. Do not add CQC/FFA/TDM to Quick Play or Custom Match before this works; [rules PR #39](https://github.com/PlayerEden/Ricochet-Rumble/pull/39), [TDM #36](https://github.com/PlayerEden/Ricochet-Rumble/issues/36), [FFA #37](https://github.com/PlayerEden/Ricochet-Rumble/issues/37).

### P1 — Next technical quality and device gates

**P1-01 Team Survival match fairness is asymmetric by design; don't mistake for competitive TDM (VERIFIED SOURCE).** Team indices alternate, so default 1 player + 2 bots yields 2 Blue vs 1 Red; 1 configured bot is expanded to 2 in team mode, returning to original 1 in FFA. This is not a scored 2v2 or 3v3 playlist; it is finite-life team elimination. Real Android teammate engagement, ally targeting and blue/red visual contrast must be confirmed by owner. Balanced scored TDM must use explicit 2v2 first and never quietly inflate a 3v2.

**P1-02 LAN protocol trust, bounds, reconnect and lifecycle (SOURCE OBSERVATION + OPEN MANUAL).** Android `ServerSocket(0,1)` accepts a LAN peer without app-level pairing/authentication, TCP is unencrypted on the local network, and `BufferedReader.readLine()` reads a complete input line *before* testing its 32,768-character ceiling. Guest-side `RR.nativeMessage` accepts host `state` packets after only basic array-length checks and assigns the nested structure directly to renderer/game state; malformed nested actor/vehicle/config objects may crash or destabilize the guest. **This is a code-level robustness risk, not a claim a real exploit was demonstrated.** Before shipping LAN: bounded framing before allocation, peer pairing/consent, strict versioned packet schemas/range checks, connection retry/timeout and two-device real-world test, ideally same controlled Wi-Fi and network-abuse tests. [LAN #22](https://github.com/PlayerEden/Ricochet-Rumble/issues/22).

**P1-03 Save continuity and fallback (VERIFIED SOURCE + OPEN MANUAL).** The only settings/profile persistence currently inspected is versioned `rr-options-v06` localStorage; no tested session/progression migration or backup. Android manifest has `android:allowBackup="false"`. Uninstalling to fix signer mismatch may erase progress/preferences. Before progression/skins/Play: define schema migration, owner-visible export/backup/restore fallback, corrupted-save recovery, and tests for upgrading without wiping. [Save contract #29](https://github.com/PlayerEden/Ricochet-Rumble/issues/29).

**P1-04 Dynamic scored spawn safety is unproven (VERIFIED SOURCE + DESIGN).** Current `respawn` picks farthest available cell and gives 1.8 sec shield but **does not evaluate ricochet bullet paths or team spawn equity**. The new pure scored spawn selector excludes blocked/occupied/bullet-close cells and discounts direct LOS, but is not wired to maze/nav/real combat; it may rank a visible position highest when no covered candidate exists, and returns `null` if no candidates. Implement a bounded delayed-retry/hold path and visual spawn guard; test death-loops and repeated spawn camping in many seeds. Don't claim flawless safe respawns now.

**P1-05 True team communication/performance (OPEN MANUAL).** Fast tests verify Blue/Red assignment, pilot armor and tanks, bot target filtering and side-winning AI logic; they do not prove that ally bots participate effectively in fights. Measure team win imbalance, player survival, meaningful ally damage, AI stall time, and frame pacing on Android. [Future feel #27](https://github.com/PlayerEden/Ricochet-Rumble/issues/27), [pilot-vs-tank balance #33](https://github.com/PlayerEden/Ricochet-Rumble/issues/33).

**P1-06 One entire natural phone match + lifecycle acceptance (OPEN MANUAL).** The owner has seen readable After Action, NEXT MATCH rotates and Lab E looks good. Specific new ally behavior and consistent occupied vehicle coloring, truthful stats after several natural matches, pause/background, battery/heat, notches, and a genuine two-phone LAN duel still need recorded results. Existing automation simulates engine hits rather than naturally finishing all matches. Keep test outcome labels separate.

### P2 — Maintainability and content polish

**P2-01 Screenshot comparison is based on an OLD ancestor (VERIFIED SOURCE).** `build-apk.yml` fallback `baseline_ref` is `dev/sector-rebound-integrated-v0920`, so the before/after captures compare modern code to v0.9.20 instead of the latest owner-accepted v0.9.25. Future CI should use an explicit trusted latest playable tag with a per-PR documented reason and compare all key gameplay states side-by-side. Current scripts assert layout and record images, not automated pixel perceptual differences.

**P2-02 Mode and cosmetic architecture need clean data boundaries.** Survival mode IDs and playlist shuffle are presently inside a monolithic game IIFE (~100 KB), while the new scored module is isolated ESM. Before adding rules editor: define one validated `MatchRules` model, share it between curated Quick Play, future Custom Match, eventual authoritative LAN host, and stable persistence. Separate team identity from optional player armor skins; keep 3v3 behind proven five-bot cap and Android performance. [Custom #38](https://github.com/PlayerEden/Ricochet-Rumble/issues/38).

**P2-03 Test matrix is strong in headless simulation but still sparse for balance.** Current existing automated suite includes 18 longer bot runs, not 50+ completed matches per proposed scored mode. 300 new maze seeds verify connectivity/spawn clearance and variety, not quality of combat encounter rate. Add CPU/FPS/latency telemetry and per-team KO distribution before setting 10/15/30-kill targets permanently. [Research](https://github.com/PlayerEden/Ricochet-Rumble/blob/main/docs/research/DEATHMATCH_BENCHMARKS_AND_BALANCE_V1_2026-10-27.md).

**P2-04 GitHub Actions and releases have costs/retention.** Full PR CI captures ~68 screenshot stages and recompiles Android. Run once per meaningful candidate, keep fast tests for every incremental code fix and archive *only final accepted* APK/artifacts permanently. Temporary full QA artifacts have 14-day retention; known-good releases and SHA/checksum manifests remain durable. Preserve readable rollback paths; never overwrite an existing tag.
